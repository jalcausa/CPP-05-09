CPP 08: contenedores con templates, iteradores y algoritmos

Para cada ejercicio: qué pide el enunciado, qué concepto quiere enseñarte, cómo lo has resuelto y qué hace cada parte del código. Al final de cada uno hay preguntas típicas de evaluación con su respuesta.

Cómo usar esta guía

El módulo 08 es el primero en el que se permite (y se exige) usar la STL. En la defensa casi todas las preguntas van a ir por tres caminos:

  1. ¿Por qué ese contenedor o algoritmo? Saber justificar vector, list, deque o stack, y std::find, std::sort, std::min_element…
  2. ¿Qué hace esta línea? Sobre todo en las partes con templates: typename, funciones miembro template, this->c.
  3. ¿Qué pasa si…? Casos límite: contenedor vacío, valor no encontrado, Span lleno, valores extremos.

Primero repasa los conceptos base y después cada ejercicio. Cada ejercicio incluye su fichero completo (pulsa sobre el nombre para desplegarlo) y fragmentos comentados. Todo está compilado y ejecutado: las salidas que ves son reales.

La STL en 5 minutos

La Standard Template Library son tres piezas que encajan entre sí:

Contenedores

Guardan datos. Son class templates: std::vector<int>, std::map<std::string, float>…

Iteradores

Objetos que "apuntan" a un elemento de un contenedor y saben avanzar. Generalizan los punteros: *it, ++it, it != end.

Algoritmos

Funciones de <algorithm> que trabajan sobre un rango [begin, end) de iteradores, sin saber qué contenedor hay debajo: std::find, std::sort, std::min_element…

La idea clave: los algoritmos no conocen los contenedores, solo los iteradores. Por eso std::find funciona igual con un vector, una list o un deque.

Categorías de iteradores

No todos los iteradores pueden hacer lo mismo. Esto explica, por ejemplo, por qué en tus tests haces it - vec.begin() con un vector pero no con una list:

  • Bidireccional (list, map): ++it y --it. No puedes restar dos iteradores ni hacer it + 5.
  • Acceso aleatorio (vector, deque): todo lo anterior, más it + n, it2 - it1, it[n] y comparar con <.

Un detalle que preguntan mucho: end() no apunta al último elemento, sino a la posición siguiente al último. Por eso los rangos son semiabiertos [begin, end) y "no encontrado" se representa devolviendo end().

Templates y typename

Un template es un molde: el compilador genera una versión concreta (una instanciación) para cada tipo con el que lo usas. easyfind(vec, 42) y easyfind(lst, 42) generan dos funciones distintas en tiempo de compilación.

¿Por qué el código de un template va en el .hpp? Porque para instanciarlo el compilador necesita ver la definición completa en cada .cpp que lo usa. Si la pusieras en un .cpp aparte, el linker no encontraría la versión para tu tipo. Por eso la regla general de 42 ("nada de implementaciones en headers") tiene una excepción explícita para los templates.

¿Para qué sirve typename delante de T::iterator? Dentro de un template, T::iterator es un nombre dependiente: depende de T, y el compilador no sabe todavía si es un tipo o, por ejemplo, una variable estática. Por defecto asume que no es un tipo. typename le dice "esto es un tipo".

typename T::iterator it;       // correcto: "T::iterator es un tipo"
T::iterator it;                // error: el compilador lo interpreta como un valor

Excepciones

En estos módulos señalas errores lanzando excepciones. Hay dos formas de hacerlo, y en tu código usas las dos:

  • Usar una de la librería estándar: throw std::runtime_error("mensaje"); (en easyfind y en RPN). Está en <stdexcept> y ya guarda el mensaje.
  • Crear tu propia clase que herede de std::exception y sobrescriba what() (en Span).
class FullContainerException : public std::exception
{
public:
    virtual const char* what() const throw();
};

const throw() significa: el método no modifica el objeto (const) y promete no lanzar excepciones (throw(), la especificación de excepciones de C++98). Tiene que coincidir con la firma de std::exception::what() para sobrescribirla. Se captura por referencia constante (catch (const std::exception& e)) para no copiar el objeto y para que el polimorfismo funcione: e.what() llama a la versión de la clase hija.

Forma canónica ortodoxa y C++98

Desde el módulo 02, toda clase debe tener: constructor por defecto, constructor de copia, operador de asignación y destructor. Todas tus clases la cumplen: Span, MutantStack, BitcoinExchange, RPN y PmergeMe.

Restricciones de C++98 que se notan en tu código:

  • No existe auto: escribes el tipo completo del iterador (std::map<std::string, double>::const_iterator).
  • No hay bucles for (x : contenedor): se recorre con iteradores o índices.
  • std::vector<std::pair<int,int> > lleva un espacio en > >, porque en C++98 >> se lee como el operador de desplazamiento.
  • Los ifstream reciben const char*, de ahí el filename.c_str().

Objetivo y reglas del módulo

Objetivo del módulo: aprender a usar la STL en lugar de reinventarla. Los tres ejercicios se podrían resolver sin STL, pero el enunciado dice explícitamente que usarla es precisamente el objetivo y que sacarás mala nota si no lo haces, aunque el código funcione.

  • ex00: escribir un algoritmo genérico (function template) que funcione con cualquier contenedor gracias a los iteradores.
  • ex01: diseñar una clase que use un contenedor por dentro y se apoye en algoritmos (sort, min_element, max_element), y aceptar rangos de iteradores.
  • ex02: entender qué es un adaptador de contenedor y cómo ampliar una clase de la STL mediante herencia.
Reglas específicas del módulo (enunciado)

Debes usar la STL, en especial los contenedores (vector/list/map…) y los algoritmos (cabecera <algorithm>), siempre que sea apropiado y tanto como puedas. Puedes definir los templates en los headers como siempre, o declararlos en el header y escribir la implementación en ficheros .tpp. Los headers son obligatorios; los .tpp, opcionales.

ex00 · Easy find

Enunciado

Ficheros: Makefile, main.cpp, easyfind.{h, hpp} y opcional easyfind.tpp.

Escribe una plantilla de función easyfind que acepte un tipo T. Recibe dos parámetros: el primero de tipo T y el segundo un entero. Suponiendo que T es un contenedor de enteros, la función debe encontrar la primera aparición del segundo parámetro en el primero. Si no se encuentra, puedes lanzar una excepción o devolver un valor de error de tu elección (inspírate en cómo se comportan los contenedores estándar). No hace falta gestionar contenedores asociativos. Entrega tus propios tests.

Qué te quiere enseñar

Que con un template y un par de iteradores puedes escribir una sola función que vale para cualquier contenedor secuencial, y que no hace falta escribir el bucle de búsqueda a mano porque ya existe std::find.

Cómo lo has resuelto

template <typename T>
typename T::iterator easyfind(T& container, int value)
{
	typename T::iterator it = std::find(container.begin(), container.end(), value);
	if (it == container.end())
		throw std::runtime_error("Value not found in container");
	return it;
}
  1. template <typename T>: T será el tipo del contenedor (std::vector<int>, std::list<int>…). El compilador lo deduce solo a partir del argumento.
  2. Tipo de retorno typename T::iterator: devuelves un iterador al elemento encontrado, no un bool ni el valor. Así quien llama sabe dónde está y puede usarlo (en el main calculas el índice con it - vec.begin()). Lleva typename porque es un nombre dependiente (ver Templates).
  3. T& container: por referencia, para no copiar el contenedor entero y para que el iterador devuelto apunte al contenedor original, no a una copia que se destruye al salir de la función (eso daría un iterador colgante).
  4. std::find(begin, end, value): recorre el rango y devuelve el iterador al primer elemento igual a value, o end si no lo encuentra. Es O(n).
  5. Si it == container.end() lanzas std::runtime_error. Elegiste excepción en lugar de devolver end(). Las dos opciones son válidas según el enunciado; la de los contenedores estándar sería devolver end(), pero la excepción obliga a quien llama a gestionar el caso.

Segunda sobrecarga con const. Hay una versión casi idéntica que recibe const T& y devuelve typename T::const_iterator. Sin ella, easyfind(cvec, 5) con un const std::vector<int> no compilaría: de un contenedor const, begin() devuelve un const_iterator, que no se puede convertir a iterator. El compilador elige la sobrecarga adecuada según si el argumento es const o no.

Preguntas típicas

¿Por qué no funciona con std::map?

Porque los elementos de un map son std::pair<const Key, Value>, no int. std::find compararía cada pair con un int y no compilaría. Además, en un map lo natural es buscar por clave con map.find(key), que es O(log n). Por eso el enunciado dice que no hace falta gestionar contenedores asociativos.

¿Funcionaría con std::stack?

No. std::stack no tiene begin()/end() ni tipo iterator, así que no compila. Ese es justo el problema que resuelve el ex02.

¿Por qué no hay .cpp de easyfind?

Porque es un template: su definición tiene que estar visible donde se instancia. El Makefile solo compila main.cpp.

¿Cuál es la complejidad?

O(n): std::find es una búsqueda lineal. No puede ser mejor porque el contenedor no está ordenado.

ex01 · Span

Enunciado

Ficheros: Makefile, main.cpp, Span.{h, hpp}, Span.cpp.

Crea una clase Span que pueda guardar un máximo de N enteros. N es un unsigned int y es el único parámetro del constructor. Debe tener addNumber() para añadir un número; si ya hay N elementos, lanza una excepción. Implementa shortestSpan() y longestSpan(), que devuelven la distancia más corta y la más larga entre todos los números guardados. Si hay 0 o 1 números, no hay distancia posible: lanza una excepción. Prueba con al menos 10 000 números. Por último, implementa una función miembro que añada un rango de iteradores de una sola vez.

Con 6, 3, 17, 9, 11 la salida esperada es 2 y 14.

Qué te quiere enseñar

A encapsular un contenedor STL dentro de una clase, a resolver problemas con algoritmos (sort, min_element, max_element) en lugar de dobles bucles, y a escribir una función que acepte cualquier rango de iteradores, como hacen los constructores y el insert de los contenedores estándar.

Diseño de la clase

private:
	unsigned int		_maxSize;   // N: capacidad máxima
	std::vector<int>	_numbers;   // los números guardados

¿Por qué vector? Solo se añade al final (push_back, O(1) amortizado), hace falta ordenar (y std::sort necesita iteradores de acceso aleatorio, así que list no vale) y la memoria contigua es lo más rápido de recorrer.

En el constructor llamas a _numbers.reserve(n): reserva memoria para n enteros de una vez y así el vector no tiene que realocar mientras se llena. No cambia size(), solo capacity().

También hay un constructor por defecto Span(), que crea un Span de capacidad 0 (cualquier addNumber lanzará excepción). Existe para cumplir la forma canónica ortodoxa. Un Span útil se crea siempre con Span(n).

addNumber

void Span::addNumber(int n)
{
	if (_numbers.size() >= _maxSize)
		throw FullContainerException();
	_numbers.push_back(n);
}

Compruebas la capacidad antes de insertar. El límite lo controlas tú con _maxSize; el vector por sí solo crecería sin límite.

shortestSpan: ordenar y mirar vecinos

long Span::shortestSpan() const
{
	if (_numbers.size() < 2)
		throw NotEnoughNumbersException();

	std::vector<int> sorted(_numbers);          // copia: el método es const
	std::sort(sorted.begin(), sorted.end());    // O(n log n)

	long shortest = static_cast<long>(sorted[1]) - sorted[0];
	for (std::vector<int>::size_type i = 2; i < sorted.size(); ++i)
	{
		long diff = static_cast<long>(sorted[i]) - sorted[i - 1];
		if (diff < shortest)
			shortest = diff;
	}
	return shortest;
}

La idea clave: una vez ordenados, la distancia mínima siempre está entre dos elementos consecutivos. Si a ≤ b ≤ c, entonces c - a ≥ c - b, así que nunca hace falta comparar elementos no adyacentes. Pasas de comparar todos con todos (O(n²)) a ordenar y hacer una pasada: O(n log n).

¿Por qué una copia? El método es const (no debe modificar el objeto) y std::sort reordena en el sitio. Copias y ordenas la copia.

Con 6, 3, 17, 9, 11 → ordenado 3, 6, 9, 11, 17 → diferencias 3, 3, 2, 6 → mínimo 2.

longestSpan: máximo menos mínimo

int minVal = *std::min_element(_numbers.begin(), _numbers.end());
int maxVal = *std::max_element(_numbers.begin(), _numbers.end());
return static_cast<long>(maxVal) - minVal;

La distancia más larga siempre es entre el mayor y el menor. No hace falta ordenar: dos pasadas O(n). min_element y max_element devuelven iteradores, por eso los desreferencias con *. Ejemplo: 17 − 3 = 14.

¿Por qué long? La distancia entre dos int puede no caber en un int: entre INT_MIN y INT_MAX hay 4 294 967 295. Si restas en int, se desborda (comportamiento indefinido) y sale un número sin sentido. Por eso se convierte uno de los operandos a long antes de restar: así la resta entera se hace en long. Convertir el resultado después ya no serviría, porque el desbordamiento habría ocurrido.

addNumbers: rango de iteradores

template <typename Iterator>
void addNumbers(Iterator begin, Iterator end)
{
	// Comprueba que todo el rango cabe antes de añadir nada
	if (static_cast<unsigned long>(std::distance(begin, end))
		> _maxSize - _numbers.size())
		throw FullContainerException();
	while (begin != end)
	{
		addNumber(*begin);
		++begin;
	}
}

Es una función miembro template dentro de una clase normal. El tipo Iterator se deduce de los argumentos, así que vale para iteradores de vector, list, deque o incluso punteros a un array (arr, arr + 5). Por ser template, su cuerpo está en el .hpp, y eso está permitido.

std::distance(begin, end) (de <iterator>) cuenta cuántos elementos hay en el rango. Se compara con el hueco libre (_maxSize - _numbers.size()) antes de insertar. Así, si el rango no cabe, se lanza la excepción y el Span queda exactamente como estaba, sin rellenarse a medias. Esto se conoce como garantía fuerte ante excepciones.

Excepciones anidadas

FullContainerException y NotEnoughNumbersException son clases anidadas dentro de Span que heredan de std::exception y sobrescriben what(). Desde fuera se nombran Span::FullContainerException.

#ifndef SPAN_HPP
# define SPAN_HPP

# include <vector>
# include <exception>
# include <iterator>

class Span
{
public:
	Span();
	Span(unsigned int n);
	Span(const Span& other);
	Span& operator=(const Span& other);
	~Span();

	void addNumber(int n);

	template <typename Iterator>
	void addNumbers(Iterator begin, Iterator end)
	{
		// Check the whole range fits before adding anything, so that a failed
		// call leaves the Span unchanged
		if (static_cast<unsigned long>(std::distance(begin, end))
			> _maxSize - _numbers.size())
			throw FullContainerException();
		while (begin != end)
		{
			addNumber(*begin);
			++begin;
		}
	}

	// long: the difference between INT_MIN and INT_MAX does not fit in an int
	long shortestSpan() const;
	long longestSpan() const;

	class FullContainerException : public std::exception
	{
	public:
		virtual const char* what() const throw();
	};

	class NotEnoughNumbersException : public std::exception
	{
	public:
		virtual const char* what() const throw();
	};

private:
	unsigned int	_maxSize;
	std::vector<int>	_numbers;
};

#endif

#include <algorithm>

// --- Constructors / Destructor ---

Span::Span() : _maxSize(0)
{
}

Span::Span(unsigned int n) : _maxSize(n)
{
	_numbers.reserve(n);
}

Span::Span(const Span& other) : _maxSize(other._maxSize), _numbers(other._numbers)
{
}

Span& Span::operator=(const Span& other)
{
	if (this != &other)
	{
		_maxSize = other._maxSize;
		_numbers = other._numbers;
	}
	return *this;
}

Span::~Span()
{
}

// --- Member functions ---

void Span::addNumber(int n)
{
	if (_numbers.size() >= _maxSize)
		throw FullContainerException();
	_numbers.push_back(n);
}

long Span::shortestSpan() const
{
	if (_numbers.size() < 2)
		throw NotEnoughNumbersException();

	std::vector<int> sorted(_numbers);
	std::sort(sorted.begin(), sorted.end());

	long shortest = static_cast<long>(sorted[1]) - sorted[0];
	for (std::vector<int>::size_type i = 2; i < sorted.size(); ++i)
	{
		long diff = static_cast<long>(sorted[i]) - sorted[i - 1];
		if (diff < shortest)
			shortest = diff;
	}
	return shortest;
}

long Span::longestSpan() const
{
	if (_numbers.size() < 2)
		throw NotEnoughNumbersException();

	int minVal = *std::min_element(_numbers.begin(), _numbers.end());
	int maxVal = *std::max_element(_numbers.begin(), _numbers.end());
	return static_cast<long>(maxVal) - minVal;
}

// --- Exception messages ---

const char* Span::FullContainerException::what() const throw()
{
	return "Span: container is full, cannot add more numbers";
}

const char* Span::NotEnoughNumbersException::what() const throw()
{
	return "Span: need at least 2 numbers to compute a span";
}

Preguntas típicas

¿Por qué no usas std::list?

std::sort requiere iteradores de acceso aleatorio y list solo tiene bidireccionales (tiene su propio list::sort(), pero es más lento por la falta de localidad de memoria). vector es la opción natural.

¿Por qué no ordenas al insertar y así shortestSpan es más rápido?

Sería posible (insertando con lower_bound), pero cada inserción costaría O(n) por el desplazamiento en el vector: O(n²) para llenarlo. Ordenar una vez al consultar, O(n log n), es mejor si se consulta poco.

¿Qué es reserve y en qué se diferencia de resize?

reserve(n) solo reserva memoria (cambia capacity). resize(n) crea n elementos (cambia size). Si usaras resize, el vector empezaría con N ceros y addNumber lo vería lleno desde el principio.

¿Cómo probarías con 100 000 números aleatorios?

Como en el último test del main: std::srand(...), rellenar un std::vector<int> con std::rand() y pasarlo con sp.addNumbers(v.begin(), v.end()). Para 100 000 basta con cambiar el 20000 en los dos sitios. Es una modificación típica que te pueden pedir en directo.

¿Por qué shortestSpan devuelve long y no int?

Porque la diferencia entre dos int puede llegar a 2³² − 1, que no cabe en un int. En macOS y Linux de 64 bits long ocupa 64 bits. El enunciado no fija el tipo de retorno, y std::cout << sp.shortestSpan() sigue funcionando igual.

¿Para qué sirve un Span() sin parámetros si no se puede llenar?

Solo para cumplir la forma canónica ortodoxa exigida desde el módulo 02. Un Span por defecto tiene capacidad 0. Se podría asignar después: Span s; s = Span(10);.

ex02 · Mutated abomination (MutantStack)

Enunciado

Ficheros: Makefile, main.cpp, MutantStack.{h, hpp} y opcional MutantStack.tpp.

std::stack es uno de los pocos contenedores de la STL que no es iterable. Para arreglarlo, escribe una clase MutantStack implementada en términos de std::stack: debe ofrecer todas sus funciones miembro y además iteradores. Si ejecutas el main de ejemplo con tu MutantStack y otra vez sustituyéndolo por un std::list (cambiando push por push_back, etc.), las dos salidas deben ser iguales. El ejemplo termina con std::stack<int> s(mstack);, que también debe compilar.

Qué te quiere enseñar

Qué es un adaptador de contenedor: std::stack no guarda datos por sí mismo, sino que envuelve otro contenedor (por defecto un std::deque) y solo te deja usar la parte de arriba (push, pop, top). Ese contenedor interno es un miembro protected llamado c. Si heredas de std::stack, puedes acceder a c y exponer sus iteradores.

// Así está definido std::stack (simplificado):
template <class T, class Container = std::deque<T> >
class stack {
protected:
    Container c;                  // <- el contenedor real
public:
    typedef Container container_type;
    void push(const T& x) { c.push_back(x); }
    void pop()            { c.pop_back(); }
    T&   top()            { return c.back(); }
    ...
};

Tu solución, parte a parte

template <typename T>
class MutantStack : public std::stack<T>

Herencia pública: un MutantStack es un std::stack. Así heredas gratis push, pop, top, size y empty (todas sus funciones, como pide el enunciado), y además std::stack<int> s(mstack); compila: el constructor de copia de stack recibe un const stack& y un MutantStack se puede pasar como tal (se copia solo la parte de stack, lo que se llama slicing).

typedef typename std::stack<T>::container_type::iterator               iterator;
typedef typename std::stack<T>::container_type::const_iterator         const_iterator;
typedef typename std::stack<T>::container_type::reverse_iterator       reverse_iterator;
typedef typename std::stack<T>::container_type::const_reverse_iterator const_reverse_iterator;

Defines los tipos de iterador reutilizando los del contenedor interno. container_type es std::deque<T>, así que MutantStack<int>::iterator es en realidad std::deque<int>::iterator. No implementas ningún iterador: tomas prestado uno que ya funciona. Hace falta typename porque son nombres dependientes de T.

iterator begin()              { return this->c.begin(); }
iterator end()                { return this->c.end(); }
const_iterator begin() const  { return this->c.begin(); }
const_iterator end() const    { return this->c.end(); }

Cada función devuelve el iterador correspondiente del contenedor interno c. Versiones normales y const (para poder iterar un const MutantStack), y también rbegin/rend para recorrer al revés.

¿Por qué this->c y no solo c? Es la pregunta estrella de este ejercicio. La clase base std::stack<T> depende del parámetro T. En la primera fase de compilación del template (antes de saber qué es T), el compilador no busca nombres dentro de bases dependientes, así que c a secas daría "use of undeclared identifier". Con this->c el nombre pasa a depender de T y la búsqueda se aplaza a cuando se instancia el template. Esto se llama two-phase name lookup. También valdría std::stack<T>::c.

MutantStack() : std::stack<T>() {}
MutantStack(const MutantStack& other) : std::stack<T>(other) {}
MutantStack& operator=(const MutantStack& other)
{
	if (this != &other)
		std::stack<T>::operator=(other);
	return *this;
}
~MutantStack() {}

Forma canónica delegando en la clase base: como no añades atributos propios, copiar el stack (que copia su deque interno) es suficiente.

Preguntas típicas

¿Qué contenedor hay debajo de tu MutantStack?

std::deque<T>, el valor por defecto del segundo parámetro de std::stack. Si quisieras otro, podrías declarar template <typename T, typename C = std::deque<T> > class MutantStack : public std::stack<T, C> y usar MutantStack<int, std::vector<int> >.

std::stack no tiene destructor virtual. ¿Es un problema heredar de él?

Solo si borras un MutantStack creado con new a través de un puntero std::stack<T>*: eso sería comportamiento indefinido. En este ejercicio nunca se hace, y como MutantStack no añade atributos, no hay nada extra que liberar.
